1. SYSTEM PURPOSE
================================================================================

BTS is being developed as an automated execution and risk-management system.

The machine-learning/signal system is Eagle.

Eagle determines trading intent.

BTS receives Eagle signals, validates them, applies local trading and risk
controls, and ultimately submits approved orders to the execution broker.

IMPORTANT ARCHITECTURAL RULE:

Eagle expresses trading intent.

BTS determines whether an order is allowed and controls actual execution.

5. EAGLE MESSAGE / PROTOCOL REQUIREMENTS
================================================================================

Important Eagle concepts:

seq
---
Authoritative ordering/replay cursor.

Ordering should use seq, NOT timestamps.

event_id
--------
Unique event identifier.

Used for idempotency / duplicate-event protection.

BTS must never create a second broker action for the same event_id.

signal_id
---------
Identifies the overall trading signal lifecycle.

Used to associate entry/update/close activity belonging to the same signal.

ts
--
Timestamp.

Used primarily for audit/display purposes, not authoritative message ordering.


Known Eagle message/lifecycle concepts include:

- fund.hello
- fund.entry
- entry-price information
- signal updates
- BUY_TO_OPEN
- SELL_TO_OPEN
- BUY_TO_CLOSE
- SELL_TO_CLOSE
- heartbeat

7. EAGLE AUTHENTICATION ERROR BEHAVIOR
================================================================================

IMPORTANT CORRECTION FROM EAGLE TEAM:

Invalid/missing API key does NOT result in WebSocket close code 4401.

Authentication is rejected BEFORE the WebSocket upgrade completes.

Expected behavior:

HTTP 401 during WebSocket upgrade
=
Authentication/API-key problem.

BTS must NOT continuously auto-retry an HTTP 401.

Repeated authentication failures may trigger temporary lockout.


HTTP 429
--------
May indicate rate limiting or too many WebSocket connections.

Eagle limits each API key to:

10 concurrent WebSocket connections.

HTTP 429 may contain Retry-After.

BTS must honor Retry-After and must not create a reconnect storm.

DESIGN RULE:

One live WebSocket per BTS process.

10. DUPLICATE / IDEMPOTENCY PROTECTION
================================================================================

CURRENTLY IMPLEMENTED:

app\idempotency_manager.py

tests\test_idempotency_manager.py


Current implementation tracks processed Eagle event_id values IN MEMORY.

Important behavior:

First occurrence:

event_id = event-001

Result:
Accepted as new and remembered.


Second occurrence:

event_id = event-001

Result:
Duplicate.

TradeCoordinator returns:

approved=False
reason="DuplicateEvent"
trade_request=None


IMPORTANT SAFETY RULE:

An event received while BTS is paused is still considered processed.

Example:

Eagle sends event-001 while BTS is paused.

Result:
TradingPaused.

Trader later resumes BTS.

Eagle replays event-001.

Result:
DuplicateEvent.

The old signal MUST NOT suddenly become executable simply because BTS was
resumed.


CURRENT LIMITATION:

Idempotency information exists only in memory.

If BTS or Windows restarts, the current manager forgets processed event IDs.

BEFORE LIVE EXECUTION:

Replace or back the in-memory system with persistent storage, most likely
SQLite.

17. TWO-TRADER FUTURE PRODUCTION PLAN
================================================================================

DO NOT implement this until the Florida BTS computer is live and stable.

Future requirement:

Support a second trader/BTS computer without allowing simultaneous execution
control over the same trading account.

Target architecture:

Only ONE BTS execution client may control an account at a time.

Potential Eagle/server handover process:

1. Trader 1 requests server-side handover pause.
2. Eagle confirms signal delivery paused.
3. Verify no signal/order remains in flight.
4. Trader 1 releases execution control.
5. Trader 2 connects and authenticates.
6. Trader 2 claims execution control.
7. Trader 2 verifies broker account/position/working-order state.
8. Trader 2 enables local BTS.
9. Trader 2 requests Eagle resume.
10. Eagle resumes new signal delivery.

Both Eagle and the receiving BTS should remain safely paused during the
handover.

Potential server commands/concepts:

HANDOVER_PAUSE
CLAIM_EXECUTION_CONTROL
RELEASE_EXECUTION_CONTROL
HANDOVER_RESUME
STATUS_REQUEST

Each BTS installation should eventually have its own:

- Client identity
- Authentication credentials
- Audit trail
- Execution ownership information

Signals generated during handover should NOT automatically be replayed and
executed if they have become stale.
