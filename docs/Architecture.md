## Development, Staging, and Production Environments

BTS uses separate environments to reduce the possibility of accidental live
trading during development and testing.

### Development

Development is used for writing code, unit testing, simulation, and fake broker
testing. It does not connect to a live CQG account.

### Staging

Staging is a full test environment that closely reproduces production behavior.

It uses:

- Test API credentials
- A staging WebSocket and REST API
- Test trading signals
- CQG demo or simulated execution
- Production-like logging, validation, replay, and reconciliation

Staging must never route an order to a live CQG account.

### Production

Production is the live environment. It receives live trading signals and may
route approved orders to the live CQG account.

### Environment Safety Rule

All environment identifiers must agree before an order may be submitted:

- Incoming message environment
- API credential environment
- BTS application mode
- CQG endpoint
- CQG account ID

If any value does not match, BTS must reject the instruction and generate an
alert.


## Order-Sizing Responsibility

The machine-learning computer does not control executable order quantity.

The ML system is responsible for generating trading intent, including:

- Signal identifier
- Event identifier
- Timestamp
- Strategy
- Symbol
- Buy, sell, exit, or other approved action
- Optional informational confidence or signal-strength values

The BTS execution computer is responsible for determining the final order
quantity.

Before an order is submitted to CQG, BTS must evaluate:

- The trader's confirmed session quantity
- Maximum contracts per order
- Maximum permitted position
- Current position
- Remaining position capacity
- Daily loss and risk limits
- Trading environment
- Trading-enabled status
- Broker, exchange, and account constraints

The final submitted quantity must not exceed any applicable limit.

The preferred operating procedure is for the trader to enter or confirm the
standard quantity before the session begins. The configuration should then be
locked while automated trading is active.

Changing quantity during a session should require:

1. Pausing new entries
2. Entering the new quantity
3. Validating it against configured limits
4. Explicitly confirming the change
5. Recording the change in the audit log
6. Resuming new entries

The ML message should not contain an authoritative executable quantity.

## Signal vs. Order

A **Signal** represents trading intent generated by the machine-learning system.

Examples:

- BUY_TO_OPEN
- SELL_TO_OPEN
- BUY_TO_CLOSE
- SELL_TO_CLOSE

A signal is **not executable**.

It expresses what the trading strategy would like to do.

Before becoming an executable order, every signal must pass through:

1. Message validation
2. Protocol validation
3. Risk management
4. Position management
5. Quantity determination
6. Trading session validation
7. Broker connectivity checks

Only after all validations succeed does BTS create an **Order**.

An **Order** is the executable instruction sent to CQG.

Orders contain broker-specific information such as:

- Quantity
- Order type
- Time in force
- Account
- Price
- Stop price
- Broker identifiers
